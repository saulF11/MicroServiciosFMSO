●

●
●
●

Pod: la unidad más pequeña que Kubernetes ejecuta: uno o varios contenedores que comparten red
y almacenamiento. Es efímero y desechable.
Deployment: declara cuántas réplicas de un pod deben existir y con qué imagen; el clúster trabaja sin
descanso para que la realidad coincida con esa declaración.
Service: nombre y dirección estables para un conjunto de pods que cambian de IP todo el tiempo.
Reparte el tráfico entre los que están listos.
Ingress: regla de entrada HTTP que publica un Service hacia afuera del clúster por nombre de host y
ruta. Necesita un controlador que la ejecute.
Manifiesto declarativo: archivo YAML que describe el estado deseado, no los pasos para llegar a él.
Se versiona en Git y se aplica con kubectl apply.
Chart: paquete de Helm: los manifiestos convertidos en plantillas más un values.yaml con los valores
que cambian entre entornos.

Repaso: La teoría —arquitectura del plano de control, planificador, controladores, bucle de reconciliación,
estrategias de despliegue azul-verde y canario, y los principios de GitOps— está en las diapositivas del Tema
7. Esta práctica es la ejecución de todo eso sobre un clúster real.

Laboratorio 0 — Verificación del entorno y creación del clúster
Un clúster de Kubernetes en la máquina de un estudiante es perfectamente posible: k3d levanta k3s dentro de
contenedores de Docker y en menos de un minuto se tiene un plano de control funcionando. Antes de crear
nada, confirme que las herramientas están instaladas.

Paso 1. Verifique las versiones instaladas
Abra una terminal en la carpeta de trabajo y ejecute:
$ docker --version
$ k3d version
$ kubectl version --client
$ helm version
$ docker ps

El último comando debe responder con una tabla, aunque esté vacía. Si responde con un error de conexión,
Docker no está iniciado y nada de lo que sigue funcionará.

Captura N.º 1: salida de los cinco comandos anteriores en su terminal, con las versiones visibles. → péguela
en la Hoja de Evidencias.

Paso 2. Cree el clúster
Un solo comando crea el servidor de control, dos nodos de trabajo y publica el puerto 80 del balanceador hacia
su máquina. Ese último detalle es el que permitirá abrir la aplicación en el navegador en el Laboratorio 3.
$ mkdir practica9-kubernetes && cd practica9-kubernetes
$ k3d cluster create com600 --agents 2 -p "8080:80@loadbalancer"
# --agents 2 crea dos nodos de trabajo
# -p publica el puerto 80 del clúster en el 8080 de su máquina

Laboratorio 1 — El despliegue imperativo y por qué no sirve
Kubernetes permite crear recursos escribiendo comandos, sin ningún archivo. Funciona, es rápido y es
exactamente lo que no vamos a hacer durante el resto de la práctica. Conviene verlo una vez para entender
qué se pierde.

Paso 1. Cree un despliegue y expóngalo con comandos sueltos
Use la imagen que su pipeline de la Práctica 8 publicó en el registro. Reemplace USUARIO por su nombre de
usuario de GitHub y la etiqueta por la que corresponda.
$ kubectl create deployment tareas --image=ghcr.io/USUARIO/tareas-api:1.0.0
$ kubectl expose deployment tareas --port=80 --target-port=3000
$ kubectl get deployment,service,pods

En pocos segundos debe haber un pod en Running y un Service con una IP interna del clúster. Si el pod queda
en ImagePullBackOff, revise el anexo de errores: casi siempre es un nombre de imagen mal escrito o un
paquete privado.

Captura N.º 3: salida de kubectl get deployment,service,pods mostrando el pod en Running. → péguela en
la Hoja de Evidencias.

Paso 2. Compruebe que la aplicación responde dentro del clúster
Todavía no hay ninguna puerta hacia afuera. kubectl port-forward abre un túnel temporal entre su máquina y
el Service, útil solo para diagnosticar.
# terminal 1
$ kubectl port-forward service/tareas 8081:80
# terminal 2
$ curl http://localhost:8081/tareas

Laboratorio 2 — Manifiestos declarativos: Deployment y Service
Ahora el mismo resultado, pero escrito. Un manifiesto declara el estado deseado; Kubernetes se encarga de
alcanzarlo y de mantenerlo. Ese archivo es el que se versiona, se revisa y, en el Laboratorio 7, se convierte en
la única fuente de verdad.

Paso 1. Escriba el Deployment
Cree la carpeta k8s/ y dentro el archivo deployment.yaml. Note que no dice cómo crear los pods: dice cuántos
deben existir y con qué imagen.
k8s/deployment.yaml

apiVersion: apps/v1
kind: Deployment
metadata:
name: tareas
spec:
replicas: 2
selector:
matchLabels:
app: tareas
template:
metadata:
labels:
app: tareas
spec:
containers:
- name: api
image: ghcr.io/USUARIO/tareas-api:1.0.0
ports: [{ containerPort: 3000 }]

PRÁCTICA N.º 9

La pieza que más confunde: selector.matchLabels y template.metadata.labels deben coincidir. El
Deployment reconoce como suyos los pods que llevan esa etiqueta; si no coinciden, el clúster acepta el
manifiesto y no crea nada útil.

Paso 2. Aplique el manifiesto y observe el resultado
kubectl apply compara lo que usted declara con lo que existe y hace lo necesario para que coincidan. Ejecutarlo
dos veces seguidas no duplica nada.
$ kubectl apply -f k8s/deployment.yaml
$ kubectl get deployment tareas
$ kubectl get pods -l app=tareas -o wide
$ kubectl describe deployment tareas | head -30

En get pods debe ver dos pods, posiblemente repartidos en nodos distintos. Fíjese en la columna NODE: el
planificador decidió dónde ponerlos sin que usted interviniera.

Captura N.º 5: salida de kubectl get pods -l app=tareas -o wide con las dos réplicas en Running y el nodo
de cada una. → péguela en la Hoja de Evidencias.

Paso 3. Lea los registros y demuestre que el pod es desechable
Vea la salida del contenedor y después borre un pod a mano. No lo reemplace usted: observe quién lo hace.
$ kubectl logs -l app=tareas --tail=20
$ kubectl delete pod -l app=tareas --field-selector=status.phase=Running \
--wait=false | head -1
$ kubectl get pods -l app=tareas -w

El controlador del Deployment nota que hay menos réplicas de las declaradas y crea las que faltan en
segundos. Corte la observación con Ctrl+C.

Esto es el bucle de reconciliación: Nadie ordenó crear un pod nuevo. El controlador compara el estado
deseado con el real y actúa. Es la misma idea que después aplicará Argo CD, pero a nivel de todo el
repositorio.

Paso 4. Escriba el Service y verifique sus endpoints
Los pods cambian de IP cada vez que nacen. El Service da un nombre estable y reparte el tráfico entre los
pods que estén listos.
k8s/service.yaml

apiVersion: v1
kind: Service
metadata:
name: tareas
spec:
selector:
app: tareas
ports:
- port: 80
targetPort: 3000

Aplíquelo y revise sus endpoints: son las IP de los pods que el Service está sirviendo en este momento. Un
Service sin endpoints es un Service que no encontró ningún pod con esa etiqueta.

Laboratorio 3 — Publicar hacia afuera con Ingress
El Service resuelve el tráfico dentro del clúster. Para que un navegador de su máquina llegue a la aplicación
hace falta una regla de entrada y un controlador que la ejecute. k3s trae Traefik ya instalado, así que solo hay
que escribir la regla.

Paso 1. Confirme que existe un controlador de Ingress
Sin controlador, un Ingress es un archivo que nadie lee: se acepta y no ocurre nada.
$ kubectl get pods -n kube-system | grep traefik
$ kubectl get ingressclass

Debe aparecer el pod de Traefik en Running y una IngressClass llamada traefik marcada como predeterminada.

Paso 2. Escriba la regla de entrada
Cree k8s/ingress.yaml. La regla dice: todo lo que llegue al host tareas.localhost por la ruta raíz va al Service
tareas en el puerto 80.
k8s/ingress.yaml

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
name: tareas
spec:
rules:
- host: tareas.localhost
http:
paths:
- path: /
pathType: Prefix
backend:

Laboratorio 4 — Configuración y secretos fuera de la imagen
La misma imagen debe poder correr en laboratorio y en producción. Lo único que cambia es la configuración,
y por eso la configuración no puede vivir dentro de la imagen. Kubernetes ofrece dos objetos para eso:
ConfigMap para lo que puede leer cualquiera y Secret para lo que no.

Paso 1. Declare la configuración no sensible
Cree k8s/configmap.yaml con los valores que cambian entre entornos y que no comprometen nada si se leen.
k8s/configmap.yaml

apiVersion: v1
kind: ConfigMap
metadata:
name: tareas-config
data:
APP_ENTORNO: "laboratorio"
APP_PAGINA_TAM: "20"

Aplíquelo con kubectl apply -f k8s/configmap.yaml.

Paso 2. Cree el Secret sin escribirlo en un archivo
Este Secret se crea con un comando, a propósito: así el valor real nunca llega al repositorio. En el Laboratorio
7 verá cómo se resuelve esto de forma definitiva.
$ kubectl create secret generic tareas-secret \

Laboratorio 5 — Sondas de salud y actualización progresiva
Un pod puede estar corriendo y no ser capaz de atender: todavía está arrancando, perdió la conexión con la
base o se quedó bloqueado. Kubernetes no lo adivina; hay que decírselo con sondas. Sin readiness, el rolling
update manda tráfico a pods que no están listos y el corte es visible.

Laboratorio 7 — GitOps con Argo CD
Hasta aquí, quien despliega es usted desde su terminal. Eso significa que el clúster puede alejarse del
repositorio sin que nadie se entere, como ya ocurrió con el rollout undo del Laboratorio 5. GitOps invierte la
dirección: el repositorio declara el estado deseado y un agente dentro del clúster trabaja permanentemente
para que la realidad coincida.

Paso 1. Instale Argo CD en el clúster
Argo CD se instala como una aplicación más, en su propio espacio de nombres.
$ kubectl create namespace argocd
$ kubectl apply -n argocd -f \
https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml
$ kubectl get pods -n argocd -w

Espere a que todos los pods pasen a Running: la primera vez tarda varios minutos porque descarga las
imágenes. Corte con Ctrl+C cuando estén todos listos.

Paso 2. Entre a la interfaz de Argo CD
La contraseña inicial del usuario admin queda guardada en un Secret. Ya sabe cómo leerlo.
$ kubectl -n argocd get secret argocd-initial-admin-secret \
-o jsonpath="{.data.password}" | base64 -d; echo
$ kubectl port-forward svc/argocd-server -n argocd 8090:443
# abra https://localhost:8090 y acepte el aviso del certificado

Paso 3. Suba los manifiestos a un repositorio y declare la Application
Suba la carpeta k8s/ a un repositorio público de GitHub. Después cree el archivo argocd/application.yaml, que
le dice a Argo CD qué repositorio vigilar y dónde aplicarlo.
argocd/application.yaml

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
name: tareas
namespace: argocd
spec:
project: default
source:
repoURL: https://github.com/USUARIO/practica9-kubernetes.git
targetRevision: main
path: k8s
destination:
server: https://kubernetes.default.svc
namespace: default
syncPolicy:
automated: { prune: true, selfHeal: true }

Aplíquelo con kubectl apply -f argocd/application.yaml. En pocos segundos la aplicación aparece en la interfaz
con su árbol de recursos.

árbol de recursos. → péguela en la Hoja de Evidencias.
